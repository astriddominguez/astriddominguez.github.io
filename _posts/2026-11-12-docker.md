"En mi máquina funciona." Seguro que lo has dicho o lo has oído alguna vez. Tu API va perfecta en tu portátil, pero en el ordenador de un compañero falla porque tiene otra versión de Python, en el servidor falta una librería del sistema y en producción la base de datos está configurada de otra forma.

**Docker** nació para acabar con ese problema. En este post te cuento qué es, qué es un **contenedor** y en qué se diferencia de una **máquina virtual**, qué son las **imágenes**, **Docker Hub**, el **Dockerfile** y **Docker Compose**, y terminamos metiendo en contenedores una API hecha con [FastAPI]({% post_url 2026-11-11-fastapi-django-flask %}) junto con su base de datos.

## ¿Qué es Docker?

[Docker](https://www.docker.com) es una herramienta que permite **empaquetar una aplicación junto con todo lo que necesita para funcionar** (el lenguaje, las librerías, las dependencias del sistema, la configuración…) en una unidad llamada **contenedor**, que se ejecuta igual en cualquier ordenador que tenga Docker instalado.

La comparación clásica es la de los **contenedores de mercancías**. Antes de que existieran, cada barco cargaba sacos, barriles y cajas de formas distintas, y cargar y descargar era un caos. Con el contenedor estándar da igual lo que haya dentro: cualquier barco, grúa o camión del mundo sabe moverlo. Docker hace lo mismo con el software: da igual que dentro haya una API en Python, una web en Node o una base de datos; cualquier máquina con Docker sabe ejecutarlo.

Docker se presentó en **2013** y, aunque la idea de los contenedores ya existía en Linux, fue Docker quien la hizo fácil de usar. Hoy es una pieza básica del desarrollo y del despliegue de aplicaciones.

## Los conceptos clave

Antes de seguir, cuatro palabras que vas a ver todo el rato:

- **Imagen:** una **plantilla** de solo lectura con todo lo necesario para ejecutar la aplicación: un sistema de archivos mínimo, el lenguaje, las librerías y tu código. Es como una **receta** o, si vienes de la programación orientada a objetos, como una **clase**.
- **Contenedor:** una imagen **en ejecución**. Es el plato cocinado a partir de la receta, o el **objeto** creado a partir de la clase. De una misma imagen puedes arrancar tantos contenedores como quieras, y cada uno está aislado de los demás.
- **Dockerfile:** el archivo de texto con las **instrucciones para construir una imagen**. La receta escrita.
- **Registro (*registry*):** un almacén de imágenes desde donde se descargan y donde se publican. El más conocido es **Docker Hub**.

```text
Dockerfile ──(docker build)──► Imagen ──(docker run)──► Contenedor
                                 │  ▲
                     (docker push)│  │(docker pull)
                                 ▼  │
                              Docker Hub
```

## Un contenedor no es una máquina virtual

Esta es la duda más habitual al empezar: si un contenedor tiene "su propio sistema", ¿no es una máquina virtual? **No**, y la diferencia es importante.

### Máquina virtual

Una **máquina virtual (VM)** simula un **ordenador completo**: un programa llamado **hipervisor** (VirtualBox, VMware, Hyper-V, KVM…) reparte el hardware real entre varias VMs, y cada una arranca **su propio sistema operativo entero**, con su propio **kernel** (el núcleo del sistema, la parte que habla con el hardware).

Si tienes tres VMs con Ubuntu, tienes **tres Ubuntu completos** funcionando a la vez, cada uno con su memoria, sus procesos del sistema y varios GB de disco.

### Contenedor

Un **contenedor** no simula ningún hardware ni arranca un sistema operativo. Es un **proceso normal** del ordenador al que el kernel **aísla** del resto, de forma que cree que está solo en la máquina: ve su propio sistema de archivos, su propia red y sus propios procesos. Todos los contenedores **comparten el kernel del sistema anfitrión**.

Para conseguirlo, Docker usa dos funciones del kernel de Linux:

- **Namespaces:** aíslan lo que el proceso puede **ver** (archivos, procesos, red, usuarios…).
- **cgroups:** limitan lo que el proceso puede **usar** (CPU, memoria…).

```text
        MÁQUINAS VIRTUALES                       CONTENEDORES

  ┌────────┐ ┌────────┐ ┌────────┐      ┌────────┐ ┌────────┐ ┌────────┐
  │ App A  │ │ App B  │ │ App C  │      │ App A  │ │ App B  │ │ App C  │
  │ Libs   │ │ Libs   │ │ Libs   │      │ Libs   │ │ Libs   │ │ Libs   │
  │ SO     │ │ SO     │ │ SO     │      └────────┘ └────────┘ └────────┘
  │invitado│ │invitado│ │invitado│      ┌──────────────────────────────┐
  └────────┘ └────────┘ └────────┘      │        Docker Engine         │
  ┌──────────────────────────────┐      └──────────────────────────────┘
  │          Hipervisor          │      ┌──────────────────────────────┐
  └──────────────────────────────┘      │ Sistema operativo (kernel)   │
  ┌──────────────────────────────┐      └──────────────────────────────┘
  │           Hardware           │      ┌──────────────────────────────┐
  └──────────────────────────────┘      │           Hardware           │
                                        └──────────────────────────────┘
```

Siguiendo con una comparación de vivienda: las máquinas virtuales son **casas independientes**, cada una con sus cimientos, su tejado y su instalación eléctrica. Los contenedores son **pisos de un mismo edificio**: cada uno tiene su puerta y su intimidad, pero comparten los cimientos y la estructura.

### Comparativa

| | Máquina virtual | Contenedor |
|---|---|---|
| **Qué virtualiza** | El hardware completo | Solo el sistema operativo (aísla procesos) |
| **Sistema operativo** | Uno completo por VM | Comparte el kernel del anfitrión |
| **Tamaño** | Varios GB | De unos pocos MB a cientos de MB |
| **Arranque** | Minutos | Segundos o menos |
| **Consumo de recursos** | Alto | Bajo: caben muchos más en la misma máquina |
| **Aislamiento** | Muy fuerte | Bueno, pero menor (comparten kernel) |
| **Otro sistema operativo** | Sí (Windows dentro de Linux, por ejemplo) | No: un contenedor Linux necesita un kernel Linux |
| **Uso típico** | Ejecutar sistemas distintos, aislamiento máximo | Empaquetar y desplegar aplicaciones |

> **¿Y en Windows o Mac?** Como los contenedores de Linux necesitan un kernel Linux, **Docker Desktop** crea por debajo una pequeña máquina virtual Linux (en Windows, a través de WSL 2) donde se ejecutan. Tú no la ves ni la gestionas, pero existe. Por eso Docker en Linux es algo más rápido y ligero.

No son tecnologías rivales: es muy habitual tener **contenedores dentro de máquinas virtuales**. De hecho, la mayoría de servidores en la nube son VMs, y dentro de ellas se ejecutan contenedores.

## Ventajas de Docker

- **Se acabó el "en mi máquina funciona":** el contenedor lleva todo lo que necesita, así que funciona igual en tu portátil, en el de tu compañero, en el pipeline de [CI/CD]({% post_url 2026-11-10-ci-cd %}) y en producción.
- **Instalación de proyectos en un comando:** una persona nueva en el equipo no tiene que pasarse un día instalando Python, PostgreSQL y Redis en las versiones correctas. Clona el repositorio, ejecuta `docker compose up` y listo.
- **Aislamiento:** cada aplicación tiene sus dependencias. Un proyecto puede usar Python 3.10 y otro Python 3.13 sin pelearse, y no "ensucias" tu ordenador instalando cosas.
- **Ligero y rápido:** arranca en segundos y consume mucho menos que una VM.
- **Probar cosas sin instalarlas:** ¿quieres probar PostgreSQL, MongoDB o Redis? Un `docker run` y lo tienes; cuando acabas, lo borras y no queda rastro.
- **Despliegue sencillo:** casi todos los servicios de la nube (AWS, Google Cloud, Azure, Render, Railway, Fly.io…) saben ejecutar una imagen de Docker. Construyes la imagen una vez y despliegas exactamente esa.
- **Escalar:** si necesitas atender más tráfico, arrancas más contenedores de la misma imagen.
- **Ecosistema enorme:** en Docker Hub hay imágenes ya preparadas de casi cualquier software.
- **Infraestructura como código:** el Dockerfile y el `compose.yaml` son archivos de texto que se guardan en Git, se revisan y tienen historial, como el resto del código.

## Desventajas

- **Curva de aprendizaje:** imágenes, capas, volúmenes, redes, puertos… al principio son muchos conceptos nuevos.
- **Aislamiento menor que una VM:** como comparten kernel, un fallo grave de seguridad en el kernel podría afectar a todos los contenedores. Para la mayoría de casos es suficiente, pero si necesitas aislamiento máximo (por ejemplo, ejecutar código de terceros que no es de fiar), una VM es más segura.
- **Datos persistentes:** los contenedores son **efímeros**: si borras uno, se pierde todo lo que había escrito dentro. Para guardar datos (como una base de datos) hay que usar **volúmenes**, y es fácil equivocarse al principio.
- **En Windows y Mac va más lento**, por la VM que hay por debajo, sobre todo al compartir muchos archivos entre tu ordenador y el contenedor.
- **Las imágenes pueden ocupar mucho** si no se construyen con cuidado, y el disco se llena de imágenes y contenedores viejos si no los limpias.
- **Depurar es algo más complicado:** hay una capa más entre tú y tu aplicación (logs, redes internas, permisos de archivos…).
- **Imágenes de terceros:** descargar una imagen de cualquiera es como ejecutar un programa de cualquiera. Hay que usar imágenes de confianza.
- **No lo resuelve todo:** para gestionar cientos de contenedores en muchos servidores hace falta un **orquestador** como Kubernetes, que es otro mundo.
- **Licencia de Docker Desktop:** es gratis para uso personal, educativo y empresas pequeñas, pero las empresas grandes tienen que pagar una suscripción. Docker Engine en Linux sigue siendo libre y gratuito.

## Instalación

- **Windows y Mac:** instala [Docker Desktop](https://docs.docker.com/get-started/get-docker/), que incluye todo (Docker Engine, la línea de comandos, Docker Compose y una interfaz gráfica).
- **Linux:** puedes instalar Docker Desktop o directamente [Docker Engine](https://docs.docker.com/engine/install/) con el gestor de paquetes de tu distribución.

Para comprobar que funciona:

```bash
docker --version
docker run hello-world
```

Si ves un mensaje que empieza por *"Hello from Docker!"*, todo está listo. Acabas de descargar tu primera imagen de Docker Hub y de ejecutar tu primer contenedor.

## Docker Hub

[Docker Hub](https://hub.docker.com) es el **registro público de imágenes** de Docker: algo así como lo que es GitHub para el código ([que no es lo mismo que Git]({% post_url 2026-11-05-git-vs-github %})), pero para imágenes. Cuando haces `docker run python` y no tienes la imagen, Docker la busca y la descarga de aquí.

Hay varios tipos de imágenes:

- **Docker Official Images:** imágenes oficiales mantenidas por Docker junto a los creadores de cada software: `python`, `node`, `postgres`, `nginx`, `redis`, `ubuntu`… Son las que debes usar siempre que puedas.
- **Verified Publisher:** imágenes publicadas por empresas verificadas.
- **Imágenes de la comunidad:** las que sube cualquier usuario, con el formato `usuario/imagen`. Úsalas con cuidado.

### Etiquetas (*tags*)

Cada imagen tiene versiones, llamadas **etiquetas**, que se escriben después de dos puntos:

```text
python:3.13          → Python 3.13 sobre Debian
python:3.13-slim     → versión reducida, mucho más pequeña
python:3.13-alpine   → sobre Alpine Linux, todavía más pequeña
postgres:17          → PostgreSQL 17
python               → equivale a python:latest
```

> `latest` **no** significa "la última versión estable", sino simplemente "la etiqueta que se usa si no pones ninguna". Para que tu proyecto no cambie solo de un día para otro, indica siempre una versión concreta.

### Subir tus propias imágenes

Con una cuenta gratuita en Docker Hub puedes publicar tus imágenes:

```bash
docker login
docker tag mi-api usuario/mi-api:1.0
docker push usuario/mi-api:1.0
```

Y cualquiera (o tu servidor) podrá descargarla con `docker pull usuario/mi-api:1.0`.

Docker Hub no es el único registro. También existen **GitHub Container Registry** (`ghcr.io`), **GitLab Container Registry**, **Amazon ECR**, **Google Artifact Registry** o **Azure Container Registry**. Todos usan el mismo formato de imagen (el estándar **OCI**), así que son intercambiables.

## Comandos básicos

Antes de escribir nuestro propio Dockerfile, juguemos con una imagen ya hecha. Vamos a arrancar un servidor web **nginx**:

```bash
docker run -d --name mi-web -p 8080:80 nginx:1.27
```

- `-d` (*detached*): lo ejecuta en segundo plano.
- `--name mi-web`: le da un nombre al contenedor (si no, Docker inventa uno).
- `-p 8080:80`: conecta el **puerto 8080 de tu ordenador** con el **puerto 80 del contenedor**. El formato es siempre `anfitrión:contenedor`.

Abre [http://localhost:8080](http://localhost:8080) y verás la página de bienvenida de nginx. No has instalado nginx en tu ordenador: está todo dentro del contenedor.

Los comandos que más vas a usar:

| Comando | Qué hace |
|---|---|
| `docker run imagen` | Crea y arranca un contenedor a partir de una imagen |
| `docker ps` | Lista los contenedores en ejecución (`-a` para ver también los parados) |
| `docker stop mi-web` | Para un contenedor |
| `docker start mi-web` | Vuelve a arrancar un contenedor parado |
| `docker rm mi-web` | Borra un contenedor (tiene que estar parado, o usa `-f`) |
| `docker logs mi-web` | Muestra lo que ha escrito el contenedor por pantalla (`-f` para seguirlo en directo) |
| `docker exec -it mi-web bash` | Abre una terminal dentro de un contenedor en marcha (en imágenes mínimas, usa `sh`) |
| `docker images` | Lista las imágenes descargadas |
| `docker pull imagen` | Descarga una imagen sin ejecutarla |
| `docker build -t nombre .` | Construye una imagen a partir del Dockerfile de la carpeta actual |
| `docker rmi imagen` | Borra una imagen |
| `docker system prune` | Borra contenedores parados, redes sin usar e imágenes huérfanas |

Para dejarlo todo limpio después de la prueba:

```bash
docker stop mi-web
docker rm mi-web
```

## El Dockerfile

Ahora toca crear **nuestra propia imagen**. Para eso se escribe un **Dockerfile**: un archivo de texto llamado exactamente `Dockerfile` (sin extensión) con las instrucciones, paso a paso, para construirla.

Vamos a meter en Docker una pequeña API con FastAPI, como la del post de frameworks. La estructura del proyecto:

```text
mi-api/
├── app/
│   └── main.py
├── requirements.txt
├── Dockerfile
├── .dockerignore
└── compose.yaml
```

El código de la API:

```python
# app/main.py
from fastapi import FastAPI

app = FastAPI()

@app.get("/usuarios/{id}")
def obtener_usuario(id: int):
    return {"id": id, "nombre": "Astrid"}
```

Las dependencias:

```text
# requirements.txt
fastapi[standard]
```

Y el **Dockerfile**:

```dockerfile
# 1. Imagen base: Python 3.13 en su versión reducida
FROM python:3.13-slim

# 2. Carpeta de trabajo dentro del contenedor
WORKDIR /code

# 3. Copiamos primero SOLO las dependencias y las instalamos
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# 4. Después copiamos el código
COPY app ./app

# 5. Documentamos el puerto que usa la aplicación
EXPOSE 8000

# 6. Comando que se ejecuta al arrancar el contenedor
CMD ["fastapi", "run", "app/main.py", "--port", "8000"]
```

Lo construimos y lo ejecutamos:

```bash
docker build -t mi-api .
docker run -d --name mi-api -p 8000:8000 mi-api
```

El `.` del final de `docker build` indica que el Dockerfile y los archivos a copiar están en la carpeta actual. Abre [http://localhost:8000/docs](http://localhost:8000/docs) y tendrás tu [Swagger UI]({% post_url 2026-11-09-swagger %}) funcionando, ahora dentro de un contenedor.

### Las instrucciones más comunes

| Instrucción | Para qué sirve |
|---|---|
| `FROM` | La imagen base de la que partes. Siempre es la primera |
| `WORKDIR` | La carpeta de trabajo dentro del contenedor (la crea si no existe) |
| `COPY` | Copia archivos de tu ordenador a la imagen |
| `RUN` | Ejecuta un comando **al construir** la imagen (instalar paquetes, por ejemplo) |
| `ENV` | Define variables de entorno |
| `ARG` | Define variables que solo existen durante la construcción |
| `EXPOSE` | Documenta en qué puerto escucha la aplicación (no lo abre por sí solo; eso lo hace `-p`) |
| `USER` | El usuario con el que se ejecutan los siguientes comandos |
| `CMD` | El comando por defecto **al arrancar** el contenedor. Se puede sobrescribir en `docker run` |
| `ENTRYPOINT` | Parecido a `CMD`, pero pensado para fijar el ejecutable principal; `CMD` le añade los argumentos |

La diferencia entre `RUN` y `CMD` confunde mucho al principio: `RUN` se ejecuta **una vez, al construir la imagen**; `CMD` se ejecuta **cada vez que arranca un contenedor**.

### Capas y caché: por qué el orden importa

Cada instrucción del Dockerfile crea una **capa** de la imagen, y Docker las guarda en **caché**. Cuando vuelves a construir, reutiliza todas las capas hasta la primera que ha cambiado, y a partir de ahí lo rehace todo.

Por eso en nuestro Dockerfile copiamos `requirements.txt` e instalamos las dependencias **antes** de copiar el código:

- Si solo cambias `main.py` (lo más habitual), Docker reutiliza la capa con las dependencias ya instaladas y la construcción tarda un segundo.
- Si hubiéramos hecho `COPY . .` al principio, cualquier cambio en el código obligaría a reinstalar todas las dependencias cada vez.

> Regla general: pon primero lo que **cambia poco** (sistema, dependencias) y al final lo que **cambia mucho** (tu código).

### El archivo .dockerignore

Igual que `.gitignore` le dice a Git qué archivos no guardar, `.dockerignore` le dice a Docker qué archivos **no copiar** a la imagen:

```text
# .dockerignore
.git
.venv
__pycache__
*.pyc
.env
.pytest_cache
```

Así la imagen es más pequeña, se construye más rápido y, muy importante, **no se cuelan secretos** como el archivo `.env`.

## Volúmenes: que los datos no se pierdan

Hemos dicho que los contenedores son **efímeros**: lo que se escribe dentro desaparece al borrar el contenedor. Para guardar datos de forma permanente se usan los **volúmenes**, que son carpetas que viven fuera del contenedor. Hay dos tipos principales:

- **Volumen gestionado por Docker** (*named volume*): Docker lo guarda donde quiere y tú solo le das un nombre. Ideal para bases de datos.

  ```bash
  docker run -d -v datos_db:/var/lib/postgresql/data postgres:17
  ```

- **Montaje de una carpeta** (*bind mount*): conectas una carpeta concreta de tu ordenador con una del contenedor. Ideal para desarrollo: cambias el código en tu editor y el contenedor lo ve al momento.

  ```bash
  docker run -d -v ./app:/code/app -p 8000:8000 mi-api
  ```

## Redes

Docker crea **redes internas** para que los contenedores se comuniquen entre sí. Dentro de una misma red, cada contenedor puede encontrar a otro **por su nombre**, como si fuera un dominio: tu API puede conectarse a la base de datos usando `db` como dirección, en lugar de una IP.

La buena noticia es que con Docker Compose no tienes que configurar nada de esto: crea la red sola.

## Docker Compose

En el mundo real, una aplicación rara vez es un solo contenedor. Lo normal es tener la **API**, una **base de datos**, quizá **Redis** para caché, un **frontend**… Arrancarlo todo con `docker run` uno a uno, con todas sus opciones, se vuelve inmanejable.

**[Docker Compose](https://docs.docker.com/compose/)** permite **describir toda la aplicación en un archivo YAML** (los mismos YAML que ya vimos en el post de [OpenAPI]({% post_url 2026-11-10-openapi %})) y arrancarla entera con un solo comando.

El archivo se llama `compose.yaml` (el nombre antiguo, `docker-compose.yml`, también funciona). Vamos a añadir una base de datos PostgreSQL a nuestra API:

```yaml
# compose.yaml
services:
  api:
    build: .                      # construye la imagen con el Dockerfile de esta carpeta
    ports:
      - "8000:8000"
    environment:
      DATABASE_URL: postgresql://agenda:secreto@db:5432/agenda
    depends_on:
      db:
        condition: service_healthy   # espera a que la base de datos esté lista
    volumes:
      - ./app:/code/app              # para ver los cambios de código al momento

  db:
    image: postgres:17               # imagen oficial de Docker Hub
    environment:
      POSTGRES_USER: agenda
      POSTGRES_PASSWORD: secreto
      POSTGRES_DB: agenda
    volumes:
      - datos_db:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U agenda"]
      interval: 5s
      retries: 5

volumes:
  datos_db:
```

Fíjate en algunos detalles:

- Cada **servicio** (`api`, `db`) es un contenedor.
- `api` se **construye** a partir de nuestro Dockerfile (`build`), mientras que `db` usa una **imagen ya hecha** de Docker Hub (`image`).
- En `DATABASE_URL`, la dirección de la base de datos es simplemente **`db`**, el nombre del servicio. Compose ha creado una red donde los contenedores se encuentran por su nombre.
- La base de datos guarda sus datos en el volumen `datos_db`, así que **no se pierden** aunque borres los contenedores.
- La base de datos **no publica su puerto** a tu ordenador: solo la API puede hablar con ella, por la red interna.

> En los apuntes de Compose antiguos verás una línea `version: "3.8"` al principio del archivo. Ya no hace falta: está obsoleta y Docker la ignora.

### Comandos de Compose

| Comando | Qué hace |
|---|---|
| `docker compose up` | Construye (si hace falta) y arranca todos los servicios |
| `docker compose up -d` | Igual, pero en segundo plano |
| `docker compose up --build` | Fuerza a reconstruir las imágenes antes de arrancar |
| `docker compose ps` | Lista los servicios y su estado |
| `docker compose logs -f api` | Muestra los logs de un servicio en directo |
| `docker compose exec db psql -U agenda` | Ejecuta un comando dentro de un servicio (aquí, la consola de PostgreSQL) |
| `docker compose stop` | Para los servicios sin borrarlos |
| `docker compose down` | Para y borra los contenedores y la red (los volúmenes se mantienen) |
| `docker compose down -v` | Lo mismo, pero borrando también los volúmenes (**adiós a los datos**) |

> Antes Compose era un programa aparte y el comando se escribía con guion: `docker-compose`. Ahora viene integrado en Docker y se escribe con espacio: `docker compose`. Verás los dos en internet; usa el segundo.

## Buenas prácticas

- **Usa imágenes oficiales** y con **versión concreta**: `python:3.13-slim`, no `python:latest`.
- **Elige imágenes pequeñas** (`slim`, `alpine`): tardan menos en descargarse y tienen menos cosas que puedan tener vulnerabilidades.
- **Ordena el Dockerfile** para aprovechar la caché: dependencias primero, código al final.
- **Usa siempre `.dockerignore`**.
- **Nunca metas secretos en la imagen** (contraseñas, claves de API, el `.env`). Cualquiera que tenga la imagen podría sacarlos. Pásalos como variables de entorno al arrancar el contenedor o con un gestor de secretos. Las contraseñas del `compose.yaml` de este post valen para desarrollo, no para producción.
- **No ejecutes como root:** por defecto, los procesos del contenedor se ejecutan como administrador. Es mejor crear un usuario sin privilegios:

  ```dockerfile
  RUN useradd --create-home appuser
  USER appuser
  ```

- **Un proceso por contenedor:** la API en uno, la base de datos en otro. No lo metas todo en el mismo.
- **Construcciones multietapa (*multi-stage builds*):** usa una imagen grande con todas las herramientas para compilar y copia solo el resultado a una imagen pequeña y limpia para ejecutar. Es muy útil en lenguajes compilados (Go, Java, una web de React…):

  ```dockerfile
  # Etapa 1: compilar la web con Node
  FROM node:22 AS compilacion
  WORKDIR /web
  COPY package*.json .
  RUN npm ci
  COPY . .
  RUN npm run build

  # Etapa 2: servir solo los archivos generados con nginx
  FROM nginx:1.27-alpine
  COPY --from=compilacion /web/dist /usr/share/nginx/html
  ```

  La imagen final no lleva Node, ni `node_modules`, ni el código fuente: solo nginx y la web ya construida.

- **Limpia de vez en cuando** con `docker system prune` para recuperar espacio en disco.

## Docker y CI/CD

Docker encaja perfectamente con lo que vimos en el post de [CI/CD]({% post_url 2026-11-10-ci-cd %}). Allí decíamos que hay que **construir el artefacto una sola vez** y desplegar exactamente ese en todos los entornos. Con Docker, ese artefacto es la **imagen**:

1. El pipeline ejecuta los tests.
2. Si pasan, construye la imagen y la etiqueta con la versión o el hash del commit.
3. La sube a un registro (Docker Hub, GitHub Container Registry…).
4. El servidor de staging y después el de producción descargan **esa misma imagen** y la ejecutan, cada uno con su propia configuración en variables de entorno.

## ¿Y después de Docker?

- **Kubernetes:** cuando tienes muchos contenedores repartidos entre muchos servidores, necesitas un **orquestador** que los arranque, los reparta, los reinicie si fallan y los escale según el tráfico. Kubernetes es el estándar; Docker Compose es para una sola máquina.
- **Podman:** una alternativa a Docker compatible con sus mismos comandos e imágenes, que funciona sin un servicio en segundo plano y sin necesidad de ser root.
- **Dev Containers:** una forma de definir tu entorno de desarrollo completo en un contenedor, que editores como VS Code abren directamente.

## Para terminar

Docker empaqueta tu aplicación con todo lo que necesita en una **imagen**, que se ejecuta como un **contenedor** igual en cualquier sitio. Un contenedor **no es una máquina virtual**: no lleva un sistema operativo completo, sino que es un proceso aislado que comparte el kernel del anfitrión, y por eso es mucho más ligero y rápido.

El flujo de trabajo se resume en tres piezas:

- **Dockerfile:** la receta para construir tu imagen.
- **Docker Hub:** el almacén de donde descargas imágenes y donde puedes publicar las tuyas.
- **Docker Compose:** el archivo que describe y arranca toda tu aplicación (API, base de datos…) con un solo comando.

Si quieres practicar, coge la agenda de contactos del [ejercicio de OpenAPI y FastAPI]({% post_url 2026-11-11-ejercicio-agenda-openapi-postman-fastapi %}), escríbele un Dockerfile, añade un `compose.yaml` con PostgreSQL y comprueba que, después de un `docker compose down` y un `docker compose up`, los contactos siguen ahí. Cuando lo consigas, prueba a borrar la carpeta del proyecto, clonarlo de nuevo y arrancarlo con un solo comando: esa es la magia de Docker.
