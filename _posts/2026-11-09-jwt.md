Los datos viajan por internet de un lado a otro, ¿qué peligro, no? Cada vez que pides algo a un servidor, este necesita saber quién eres y si tienes permiso para hacerlo. Para eso se utilizan los tokens: un código único que te identifica y que viaja con cada petición para demostrar que eres tú.

## ¿Qué es un token?

Un token es una cadena de texto que te da el servidor cuando te identificas, por ejemplo al iniciar sesión en cualquier aplicación. A partir de ese momento, envías el token en cada petición que haces. Normalmente va en una cabecera como esta:

```
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
```

*Bearer* significa "portador": quien lleva el token tiene el acceso. Por eso, si alguien te lo roba, puede hacerse pasar por ti.

### ¿Por qué son importantes?

- **HTTP no tiene memoria.** El servidor no recuerda que hace un segundo iniciaste sesión. El token se lo recuerda en cada petición.
- **La contraseña viaja lo mínimo.** Solo se envía al iniciar sesión; el resto del tiempo viaja el token. ¿La ventaja? El token caduca (por ejemplo, a los 15 minutos), así que si te lo roban, pasado ese tiempo ya no sirve para nada.
- **Indica qué puedes hacer.** El token puede decir si el usuario tiene permisos básicos, de administrador, etc. Así no todos los usuarios tienen acceso a todo.

Por eso los tokens son tan importantes en el backend: no hacen que una aplicación sea invulnerable, pero son una pieza clave para controlar quién entra y qué puede hacer.

### Tipos de tokens

#### Según su formato

- **Opaco:** un identificador aleatorio que no significa nada por sí mismo. El servidor tiene que buscarlo en la base de datos para saber de quién es.
- **Autocontenido:** lleva la información dentro (quién eres, cuándo caduca, qué permisos tienes) y va firmado, así que el servidor no necesita consultar la base de datos. El ejemplo más conocido es el **JWT** (*JSON Web Token*).

¿Cuándo usar uno u otro?

| | Opaco | Autocontenido (JWT) |
|---|---|---|
| **Ventajas** | Se puede anular al momento (basta con borrarlo de la base de datos). Si alguien lo ve, no puede sacar información de él. | No hace falta consultar la base de datos en cada petición, así que es más rápido y funciona bien cuando hay varios servidores. |
| **Desventajas** | Hay que consultar la base de datos en cada petición. | No se puede anular fácilmente antes de que caduque. Cualquiera puede leer lo que lleva dentro. |
| **Se suele usar en** | Webs clásicas con sesión, o cuando necesitas poder cerrar la sesión de alguien al instante. | APIs, apps móviles y sistemas con muchos servicios. |

En la práctica es habitual combinarlos: un JWT de corta duración para las peticiones y un token opaco, guardado en la base de datos, para renovarlo.

#### Según para qué se utilizan

- **Access token:** el que envías en cada petición. Dura poco, entre unos minutos y una hora.
- **Refresh token:** dura más, días o semanas. Sirve para pedir un access token nuevo sin tener que volver a iniciar sesión.
- **ID token:** dice quién es el usuario (nombre, email…). Se usa, por ejemplo, en los botones de "Iniciar sesión con Google".

## ¿Qué es un JWT?

Un JWT (*JSON Web Token*) es el tipo de token autocontenido más usado. Tiene esta pinta:

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

Parece un churro de letras sin sentido, pero si te fijas tiene **tres partes separadas por puntos**:

| Parte | Qué contiene | En este ejemplo |
|---|---|---|
| **Header** (cabecera) | Qué tipo de token es y con qué algoritmo se ha firmado. | `{"alg":"HS256","typ":"JWT"}` |
| **Payload** (contenido) | Los datos, que se llaman *claims*. | `{"sub":"1234567890","name":"John Doe","iat":1516239022}` |
| **Signature** (firma) | Un "sello" que se calcula con el header, el payload y una clave secreta que solo conoce el servidor. | `SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c` |

Algunos *claims* que vas a ver mucho:

- `sub`: de quién es el token (normalmente el id del usuario).
- `iat`: cuándo se creó.
- `exp`: cuándo caduca.
- `iss`: quién lo ha emitido.

Las fechas van en segundos contados desde 1970, así que `1516239022` es el 18 de enero de 2018.

## Firmado, no cifrado

Esta es la idea más importante del post, y la que a mí más me sorprendió: **un JWT no es secreto**.

Esas letras raras no están cifradas, solo están **codificadas en Base64**. Codificar no es lo mismo que cifrar: cualquiera puede deshacerlo sin ninguna clave. Si tienes una terminal a mano, pruébalo:

```bash
echo "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9" | base64 -d
# {"alg":"HS256","typ":"JWT"}
```

Entonces, ¿para qué sirve la firma? **No sirve para ocultar, sirve para que nadie pueda modificarlo.** Si alguien cambia en el payload `"rol":"usuario"` por `"rol":"admin"`, la firma deja de coincidir y el servidor rechaza el token. Para crear una firma válida haría falta la clave secreta, y esa solo la tiene el servidor.

Es como una carta en un sobre transparente con un sello de lacre: todo el mundo puede leerla, pero nadie puede cambiarla sin romper el sello.

¿Qué significa esto en la práctica?

- **Nunca pongas contraseñas ni datos sensibles en el payload.** Cualquiera que tenga el token puede leerlos.
- **Envía los tokens siempre por HTTPS**, para que nadie los pueda interceptar por el camino.
- Si de verdad necesitas que el contenido sea secreto, existe una variante cifrada llamada JWE, pero eso ya es para otro día.

## Pruébalo tú: jwt.io

La mejor forma de entenderlo es verlo. Entra en [jwt.io](https://jwt.io) y pega el token de ejemplo de arriba. Verás que la web te enseña el header y el payload perfectamente legibles, sin pedirte ninguna clave.

Ahora haz la prueba:

1. Escribe `your-256-bit-secret` en el campo del secreto: la web te dirá que la firma es válida.
2. Cambia una sola letra del secreto: la firma deja de ser válida.

Leer el token lo puede hacer cualquiera, pero comprobar (y crear) una firma válida solo lo puede hacer quien conoce la clave exacta.

> **Ojo:** no pegues nunca tokens reales de tu trabajo o de una aplicación en producción en ninguna web, tampoco en jwt.io. Un token que todavía no ha caducado es como prestarle a alguien tu llave.

## Errores comunes

- **Guardar datos sensibles en el payload.** Ya lo hemos visto: se puede leer.
- **Tokens que no caducan.** Un token sin `exp` le sirve para siempre a quien lo robe.
- **Usar una clave secreta débil** como `"123456"`. Se puede adivinar probando combinaciones, y con ella cualquiera podría firmar sus propios tokens.
- **No verificar la firma en el servidor.** Si el servidor se cree lo que dice el payload sin comprobar el sello, todo lo anterior no sirve de nada.

## Para terminar

Los tokens son la forma de decirle al servidor "soy yo" en cada petición sin enviar la contraseña todo el rato. El JWT es el más popular porque lleva la información dentro y el servidor no necesita consultar la base de datos. Pero recuerda: **está firmado, no cifrado**. Cualquiera puede leerlo; lo que nadie puede hacer es modificarlo sin que se note.
