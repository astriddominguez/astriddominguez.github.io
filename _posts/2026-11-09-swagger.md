En el [post anterior]({% post_url 2026-11-09-que-es-una-api %}) comparamos una API con un restaurante: tú le pides al camarero (la API) lo que quieres, y la cocina (el servidor) lo prepara. Pero para pedir algo necesitas saber qué hay en la **carta**. Si tú creas una API, ¿cómo sabe otra persona qué tiene la carta de la tuya?

Aquí es donde entra **Swagger**.

## El problema: una API sin instrucciones

Imagina que te pasan la URL de una API y te dicen "úsala". Enseguida te surgen preguntas:

- ¿Qué endpoints tiene?
- ¿Qué método uso en cada uno: GET, POST, PATCH…?
- ¿Qué datos tengo que enviar, y en qué formato?
- ¿Qué me va a devolver? ¿Y qué códigos de estado puede dar?
- ¿Necesito un token?

Sin documentación solo te quedan malas opciones: preguntarle a quien la programó (que igual ya no está en el equipo), ponerte a leer su código o probar a ciegas hasta que algo funcione. Es como ir a un restaurante sin carta y tener que adivinar los platos.

## ¿Qué es Swagger?

Swagger es un **conjunto de herramientas para documentar APIs y trabajar con ellas**.

Si me quedo con una sola idea: Swagger coge la descripción de tu API y la convierte en una **página web que cualquiera puede leer y probar**, sin instalar nada.

## Swagger UI: la carta interactiva

La herramienta más conocida de Swagger es **Swagger UI**, y es la que verás en la mayoría de proyectos. Es una página web que muestra:

- **Todos los endpoints**, agrupados por temas (usuarios, productos, pedidos…).
- **El método HTTP de cada uno**, con su propio color: GET en azul, POST en verde, PUT en naranja, DELETE en rojo… Así se ve de un vistazo qué hace cada uno.
- **Los parámetros y el cuerpo** que tienes que enviar, con ejemplos.
- **Las posibles respuestas**: qué datos devuelve y con qué [códigos de estado]({% post_url 2026-11-09-que-es-una-api %}#los-códigos-de-estado).
- **Si necesita autenticación**: un botón **Authorize** donde pegas tu token una vez y se envía en todas las peticiones.

Y lo mejor: no solo puedes leerla, también puedes **probarla**. Cada endpoint tiene un botón **Try it out** que te deja rellenar los datos y hacer una petición de verdad desde el navegador.

Volviendo al restaurante: Swagger UI es una carta en la que, además de leer los platos, puedes pedirlos y ver lo que te traen al momento.

## Pruébalo tú: un paseo por la demo Petstore

Swagger tiene una demo pública de una tienda de mascotas, **Petstore**, pensada justo para practicar. Vamos a pedir los datos de una mascota:

1. Abre [https://petstore.swagger.io](https://petstore.swagger.io). Verás la lista de endpoints agrupados en tres temas: `pet`, `store` y `user`.
2. Busca el endpoint azul **`GET /pet/{petId}`** y haz clic para desplegarlo. Verás que pide un parámetro, `petId`: el id de la mascota.
3. Pulsa **Try it out**. El campo `petId` se vuelve editable: escribe un número, por ejemplo `1`.
4. Pulsa **Execute**.

Debajo aparecen tres cosas muy útiles:

- **Curl:** el comando equivalente para hacer la misma petición desde la terminal.
- **Request URL:** la URL exacta a la que se ha enviado la petición.
- **Server response:** el código de estado y el JSON que ha devuelto el servidor.

Si la mascota existe, recibirás un **200** con sus datos. Prueba ahora con un id que no exista, como `999999`: recibirás un **404** con el mensaje `Pet not found`.

> La demo es pública y cualquiera puede crear o borrar mascotas, así que puede que el id `1` no exista cuando lo pruebes. Si te sale un 404, prueba con otro número.

Sin escribir nada de código ya sabes qué endpoints tiene la API, qué piden y qué devuelven. Eso es lo que consigue Swagger.

## ¿De dónde saca Swagger la información?

Swagger UI no se inventa nada: lee un **archivo que describe la API**, escrito en YAML o JSON y siguiendo un estándar llamado **OpenAPI**. En ese archivo se apunta cada endpoint, sus parámetros, sus respuestas, la autenticación…

Para que te hagas una idea, así se describiría el endpoint `GET /usuarios/{id}` del post anterior:

```yaml
paths:
  /usuarios/{id}:
    get:
      summary: Obtener un usuario por su id
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: integer
      responses:
        "200":
          description: El usuario existe
        "404":
          description: El usuario no existe
```

Aunque no conozcas el formato, se entiende bastante bien. Swagger UI lee esto y lo convierte en la página que has visto en la demo.

OpenAPI da para mucho más, así que le dedicaré su propio post.

## La confusión típica: ¿Swagger u OpenAPI?

Vas a ver que mucha gente usa "Swagger" y "OpenAPI" como si fueran lo mismo. Tiene su explicación:

Al principio, todo se llamaba Swagger: tanto el formato del archivo como las herramientas. En **2016**, el formato pasó a manos de una organización independiente y se renombró como **OpenAPI**. Las herramientas siguieron llamándose Swagger.

Así que hoy:

| | Qué es | En el restaurante |
|---|---|---|
| **OpenAPI** | El estándar: cómo se escribe el archivo que describe la API | El contenido de la carta |
| **Swagger** | Las herramientas que trabajan con ese archivo | La carta impresa y bonita que te dan en la mesa |

Si alguien te dice "el Swagger de la API", casi siempre se refiere a la página de Swagger UI o al archivo OpenAPI que hay detrás.

## Otras herramientas de Swagger

Swagger UI es la estrella, pero no es la única:

- **Swagger Editor:** un editor para escribir el archivo OpenAPI viendo el resultado a la vez. Tiene una versión online en [editor.swagger.io](https://editor.swagger.io).
- **Swagger Codegen:** genera código a partir del archivo, por ejemplo un cliente para llamar a la API desde otro lenguaje, sin escribirlo a mano.

## Cómo añadir Swagger a tu propia API

La buena noticia es que normalmente no tienes que escribir el archivo OpenAPI a mano: muchos frameworks lo **generan a partir de tu código** y te montan Swagger UI casi sin hacer nada.

| Framework | Lenguaje | Cómo |
|---|---|---|
| **FastAPI** | Python | Viene incluido, en `/docs` |
| **Spring Boot** | Java | Con la librería `springdoc-openapi`, en `/swagger-ui.html` |
| **Express** | JavaScript (Node) | Con la librería `swagger-ui-express` |

Por ejemplo, con FastAPI basta con esto:

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/usuarios/{id}")
def obtener_usuario(id: int):
    return {"id": id, "nombre": "Astrid"}
```

Lo arrancas con `fastapi dev main.py`, abres [http://127.0.0.1:8000/docs](http://127.0.0.1:8000/docs) y ya tienes tu Swagger UI con el endpoint `GET /usuarios/{id}`, listo para probar con **Try it out**. Fíjate en que FastAPI ha entendido solo que `id` es un número entero, porque lo hemos puesto en el código (`id: int`).

Una ventaja enorme de generarlo desde el código: la documentación **no se queda desactualizada**. Si cambias un endpoint, la página cambia con él.

## Para terminar

Swagger es un conjunto de herramientas para documentar APIs, y la más conocida es **Swagger UI**: una página web donde cualquiera puede ver qué endpoints tiene una API, qué datos piden, qué devuelven y probarlos desde el navegador. Por detrás, Swagger lee un archivo escrito con el estándar **OpenAPI**, que muchos frameworks generan solos a partir de tu código.
