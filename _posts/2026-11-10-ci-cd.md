Este blog lo escribo en archivos de texto en mi ordenador, con Git. Cuando termino un post, hago `git push` y, un par de minutos después, ya está publicado en internet. Yo no subo archivos a ningún servidor ni ejecuto nada más: GitHub detecta el push, construye la web y la publica él solo.

Sin saberlo, ya estaba usando **CI/CD**. En este post te cuento qué es, por qué se considera una buena práctica y cómo montar tu primer flujo con GitHub Actions.

> Si todavía no te manejas con Git, empieza por los [comandos básicos]({% post_url 2026-11-05-git-comandos-basicos %}) y por la diferencia entre [Git y GitHub]({% post_url 2026-11-05-git-vs-github %}).

## El problema: "en mi ordenador funciona"

Imagina un equipo trabajando sin CI/CD:

- Cada persona prueba el código en su ordenador… si se acuerda. Y cada ordenador tiene sus versiones, sus librerías y sus configuraciones.
- Alguien sube a `main` un cambio que rompe algo, y nadie se entera hasta días después, cuando ya hay otros diez cambios encima y cuesta saber cuál fue el culpable.
- Publicar una versión nueva es un proceso manual: conectarse al servidor, copiar archivos, ejecutar comandos en un orden concreto… Si se te olvida un paso, la web se cae.
- Como publicar da miedo, se hace poco. Y como se hace poco, cada publicación lleva muchísimos cambios a la vez, así que da todavía más miedo.

La frase más famosa de este caos es **"pues en mi ordenador funciona"**. CI/CD existe para que eso deje de importar.

## ¿Qué es CI? Integración continua

CI viene de *Continuous Integration*, **integración continua**.

La idea es que, **cada vez que alguien sube código** (un push o un pull request), un servidor descarga ese código y ejecuta automáticamente una serie de comprobaciones:

- Instalar las dependencias.
- Compilar o construir el proyecto.
- Pasar los tests.
- Revisar el estilo del código con un *linter*.

Si todo va bien, verás un ✅ verde al lado de tu commit en GitHub. Si algo falla, verás una ❌ roja y te llegará un aviso.

Lo importante es que estas comprobaciones se ejecutan **siempre**, en una máquina limpia y **igual para todo el mundo**. Ya no depende de que alguien se acuerde de pasar los tests, ni de cómo tenga configurado su ordenador.

Y lo de "continua" viene de otra idea clave: integrar cambios **pequeños y a menudo**. Es mucho más fácil encontrar un error en un cambio de 20 líneas que en uno de 2000.

## ¿Qué es CD? Entrega y despliegue continuos

Con la CD hay un pequeño lío, porque la D puede significar dos cosas:

- **Continuous Delivery (entrega continua):** cada cambio que pasa la CI queda **listo para publicarse**, pero es una persona la que decide cuándo y pulsa el botón.
- **Continuous Deployment (despliegue continuo):** cada cambio que pasa la CI se **publica solo**, sin que nadie pulse nada.

La diferencia es solo ese último paso: si hay o no un botón que pulsa una persona. Muchas empresas usan la entrega continua para su web de producción, porque prefieren decidir el momento exacto en que sale una versión nueva.

Este blog, por cierto, usa despliegue continuo: cada push a `main` se publica directamente.

## Cómo encaja todo: el pipeline

El conjunto de pasos que se ejecutan uno detrás de otro se llama **pipeline** (tubería). Uno típico sería:

```
git push → 1. Construir → 2. Tests → 3. Publicar en pruebas → 4. Publicar en producción
```

Los dos primeros pasos son la CI, y los dos últimos son la CD.

Funciona como una cadena de montaje con un control de calidad en cada puesto: si un paso falla, **el pipeline se para** y el código no avanza al siguiente. Si los tests fallan, no se publica nada. Así lo que está roto nunca llega a los usuarios.

Puedes ver el pipeline de este blog en la pestaña **Actions** de su repositorio en GitHub: cada push aparece como una ejecución llamada *pages build and deployment*, con su ✅ o su ❌.

## CI en la práctica: GitHub Actions

**GitHub Actions** es la herramienta de CI/CD que viene integrada en GitHub. Es gratis en los repositorios públicos y, en los privados, incluye unos minutos gratis al mes.

Para usarla, solo tienes que crear un archivo YAML dentro de la carpeta `.github/workflows/` de tu proyecto. Este, por ejemplo, ejecuta los tests de un proyecto en Python cada vez que se sube código a `main` o se abre un pull request:

```yaml
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-python@v6
        with:
          python-version: "3.13"
      - run: pip install -r requirements.txt
      - run: pytest
```

> Si no has visto YAML nunca, en el [post de OpenAPI]({% post_url 2026-11-10-openapi %}) tienes un repaso rápido.

Vamos por partes:

- **`name`**: el nombre del flujo, que verás en la pestaña Actions.
- **`on`**: **cuándo** se ejecuta. Aquí, con cada push a `main` y con cada pull request.
- **`jobs`**: los trabajos que hay que hacer. Aquí hay solo uno, que he llamado `tests`.
- **`runs-on`**: en qué máquina se ejecuta. `ubuntu-latest` es un ordenador Linux limpio que GitHub prepara para ti y que se borra al terminar.
- **`steps`**: los pasos, en orden. Hay dos tipos:
  - **`uses`**: usa una *action*, un paso ya hecho por otra persona. `actions/checkout` descarga tu código en la máquina, y `actions/setup-python` instala Python.
  - **`run`**: ejecuta un comando, igual que lo harías en tu terminal. Aquí instalamos las dependencias y pasamos los tests con `pytest`.

Si `pytest` encuentra un test que falla, el paso falla, el flujo se para y aparece la ❌ roja. En un pull request la verás justo encima del botón de *Merge*, así que quien lo revise sabe al momento si el cambio rompe algo.

## CD en la práctica: publicar automáticamente

Con la CI sabemos que el código funciona. Ahora toca la otra mitad: hacerlo llegar a los usuarios.

### Los entornos

Antes de ver el ejemplo, un concepto importante. Normalmente una aplicación no se publica en un solo sitio, sino en varios **entornos**:

| Entorno | Para qué sirve | Quién lo usa |
|---|---|---|
| **Desarrollo** | Programar y probar mientras trabajas | Tú, en tu ordenador |
| **Staging** (o preproducción) | Probar la versión nueva en un sitio igual que el real | El equipo |
| **Producción** | La aplicación de verdad | Los usuarios |

**Staging** es un ensayo general: una copia de producción, con la misma configuración pero con datos de prueba. Ahí se comprueba que todo funciona en un entorno real antes de que lo vean los usuarios. Lo que falla en staging no le afecta a nadie.

Un pipeline de CD típico lleva cada cambio primero a staging y, si todo va bien, a producción.

### Añadir el despliegue al flujo

Vamos a ampliar el `ci.yml` de antes con un segundo job que publique la aplicación:

{% raw %}
```yaml
# .github/workflows/ci.yml
name: CI/CD

on:
  push:
    branches: [main]
  pull_request:

jobs:
  tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-python@v6
        with:
          python-version: "3.13"
      - run: pip install -r requirements.txt
      - run: pytest

  desplegar:
    needs: tests
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    environment: produccion
    steps:
      - uses: actions/checkout@v5
      - run: ./desplegar.sh
        env:
          DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}
```
{% endraw %}

Lo nuevo está en el job `desplegar`:

- **`needs: tests`**: solo se ejecuta si el job `tests` ha terminado bien. Si un test falla, no se despliega. Este es el "control de calidad" del pipeline.
- **`if: github.event_name == 'push'`**: solo se despliega con un push a `main`, no con los pull requests. Tiene sentido: un pull request es un cambio que todavía se está revisando, así que lo probamos, pero no lo publicamos.
- **`environment: produccion`**: le dice a GitHub que este job publica en el entorno de producción. Ahora vemos para qué sirve.
- **`./desplegar.sh`**: el script que publica la aplicación, con un token guardado como secreto (en las buenas prácticas veremos por qué). Lo que haga por dentro depende de dónde esté alojada tu aplicación: subir los archivos a un servidor, crear una imagen de Docker, avisar a un servicio como Render o Railway… Muchos de esos servicios tienen ya su propia *action*, así que a veces ni siquiera tienes que escribir el script.

### De despliegue continuo a entrega continua con un botón

Tal y como está, este flujo es **despliegue continuo**: cada push a `main` que pasa los tests se publica solo.

¿Y si prefieres que una persona dé el visto bueno antes de publicar? Es decir, **entrega continua**. En GitHub no hace falta cambiar el flujo: ve a *Settings → Environments*, crea el entorno `produccion` y activa la regla **Required reviewers** con las personas que pueden aprobar.

A partir de ahí, cuando el pipeline llegue al job `desplegar`, se quedará en pausa esperando. Una de esas personas entra en la pestaña Actions, revisa el cambio y pulsa **Approve and deploy**. Ese es el famoso "botón" de la entrega continua.

> En los repositorios públicos esta regla es gratis. En los privados depende del plan de GitHub que tengas.

Con varios entornos puedes combinar las dos cosas: desplegar automáticamente en `staging` y pedir aprobación para `produccion`.

## Buenas prácticas de CI

Tener un pipeline no sirve de mucho si no se usa bien. Estas son las prácticas que marcan la diferencia en la parte de CI.

### Commits pequeños y frecuentes

Cuanto más pequeño es un cambio, más fácil es revisarlo y, si rompe algo, más fácil es encontrar el error. Mejor diez commits pequeños al día que uno enorme a la semana. Y si además siguen [Conventional Commits]({% post_url 2026-11-05-git-conventional-commits %}), el historial se entiende de un vistazo.

### No subas directamente a main

Trabaja en una [rama]({% post_url 2026-11-05-git-comandos-basicos %}) y abre un *pull request* para unirla a `main`. Así la CI comprueba tu cambio **antes** de que llegue a `main`, y otra persona puede revisarlo.

### Protege main

En GitHub puedes configurar reglas para la rama `main` (en *Settings → Rules*) y exigir que la CI haya pasado antes de poder fusionar un pull request. Así nadie puede colar un cambio roto, ni siquiera sin querer. Es la forma de que la regla anterior no dependa de la buena voluntad de cada uno.

### Si la CI se rompe, arreglarla es lo primero

Una CI en rojo que nadie arregla acaba ignorándose: si siempre falla, nadie se fija en si falla por algo nuevo. Cuando `main` se rompe, lo prioritario es dejarla en verde otra vez, ya sea arreglando el error o deshaciendo el cambio que lo causó.

### Pipelines rápidos

Si la CI tarda 40 minutos, la gente deja de esperarla y se pone a hacer otra cosa. Intenta que tarde pocos minutos: ejecuta primero las comprobaciones más rápidas, guarda en caché las dependencias para no descargarlas siempre y separa en otro flujo las pruebas muy lentas.

### La CI es tan buena como tus tests

Un ✅ verde solo significa que los tests han pasado. Si no tienes tests, o no prueban nada importante, la CI te dirá que todo va bien aunque esté roto. Escribir buenos tests es la base de todo lo demás.

### Las mismas versiones en todas partes

Para acabar de verdad con el "en mi ordenador funciona", la CI tiene que usar las mismas versiones que tu ordenador y que el servidor: la misma versión de Python (por eso la indicamos en el flujo) y las mismas versiones de las librerías (por eso las fijamos en `requirements.txt`).

## Buenas prácticas de CD

Publicar automáticamente es muy cómodo, pero también significa que un error puede llegar a los usuarios muy rápido. Estas prácticas hacen que desplegar sea seguro.

### Despliegues pequeños y frecuentes

Lo mismo que con los commits: es mucho menos arriesgado publicar un cambio pequeño cada día que cien cambios juntos una vez al mes. Si algo falla, sabes exactamente qué ha sido. Al principio da vértigo publicar tan a menudo, pero en realidad es lo que hace que publicar deje de dar miedo.

### Pasa siempre por staging

No publiques en producción algo que no haya funcionado antes en staging. Los tests comprueban el código, pero staging comprueba que todo funciona junto en un entorno real: la base de datos, la configuración, los otros servicios con los que habla tu aplicación…

### Construye una vez y despliega lo mismo en todas partes

Construye la aplicación **una sola vez** al principio del pipeline y despliega exactamente ese resultado (lo que se llama un *artefacto*: un paquete, una imagen de Docker…) en staging y después en producción. Si vuelves a construirla para cada entorno, lo que llega a producción podría no ser exactamente lo que probaste en staging. Entre un entorno y otro solo debe cambiar la configuración, como la dirección de la base de datos.

### Ten siempre un plan para volver atrás

Por muy bien que lo hagas, algún día se colará un error en producción. Lo importante es poder volver a la versión anterior (hacer un **rollback**) en minutos, sin ponerte a arreglar el código con prisas. Para eso ayuda mucho marcar cada versión publicada con un tag de Git, como vimos en el post de [Conventional Commits]({% post_url 2026-11-05-git-conventional-commits %}#esto-conecta-con-las-versiones): así sabes exactamente qué código hay en cada versión y a cuál volver.

### Comprueba que el despliegue ha funcionado

Que el script de despliegue termine sin errores no significa que la aplicación funcione. Añade al final del pipeline una comprobación rápida (un *smoke test*): por ejemplo, hacer una petición a la API y comprobar que responde con un `200`. Y una vez publicada, vigila si aparecen más errores de lo normal.

### Separa desplegar de activar

Con las ***feature flags*** (interruptores de funcionalidades) puedes publicar código nuevo **apagado**, y encenderlo cuando quieras sin volver a desplegar. Así puedes subir a producción una funcionalidad a medio hacer sin que nadie la vea, activarla primero solo para tu equipo, o apagarla al momento si da problemas.

### Despliegues graduales

En aplicaciones con muchos usuarios no se cambia todo de golpe. Dos estrategias muy habituales:

- **Canary:** la versión nueva se publica primero para un porcentaje pequeño de usuarios (por ejemplo, el 5 %). Si todo va bien, se va ampliando hasta llegar al 100 %. El nombre viene de los canarios que bajaban los mineros a las minas para detectar gases antes que ellos.
- **Blue-green:** tienes dos copias de producción, la "azul" (la actual) y la "verde" (la nueva). Publicas en la verde, la compruebas y cambias el tráfico de una a otra de golpe. Si algo falla, vuelves a la azul en segundos.

Para empezar no te hacen falta, pero está bien saber que existen.

### Nunca pongas contraseñas en el código

Para publicar, el pipeline suele necesitar contraseñas, claves o tokens. Nunca los escribas en el archivo YAML ni en el código: cualquiera con acceso al repositorio los vería, y quedarían para siempre en el historial de Git.

En su lugar, guárdalos como **secretos** en GitHub (*Settings → Secrets and variables → Actions*) y úsalos así en el flujo:

{% raw %}
```yaml
- run: ./publicar.sh
  env:
    API_TOKEN: ${{ secrets.API_TOKEN }}
```
{% endraw %}

GitHub los guarda cifrados y, si aparecen en los logs, los oculta con asteriscos. Además, puedes guardar secretos distintos para cada entorno: así staging nunca usa por error las claves de producción.

## Herramientas populares

GitHub Actions no es la única opción. Estas son algunas de las más usadas:

| Herramienta | Qué es |
|---|---|
| **GitHub Actions** | La de GitHub, integrada en cada repositorio |
| **GitLab CI/CD** | La equivalente de GitLab, también integrada |
| **Jenkins** | Un clásico de código abierto que instalas en tu propio servidor |
| **CircleCI** | Un servicio externo que se conecta a GitHub o a otras plataformas |
| **Bitbucket Pipelines** | La de Bitbucket, la plataforma de Atlassian |

Cada una tiene su propio formato de archivo, pero la idea es la misma en todas: un archivo que dice **cuándo** se ejecuta el pipeline y **qué pasos** sigue.

## Para terminar

La **CI** comprueba automáticamente cada cambio que subes, y la **CD** lo lleva por los distintos entornos hasta producción, sola o con la aprobación de una persona. Juntas te permiten publicar más a menudo y con menos miedo: si algo se rompe, te enteras al momento, no llega a los usuarios y, si llega, puedes volver atrás en minutos.

Si quieres probarlo, crea un repositorio con un par de tests, añade el archivo `ci.yml` de este post y haz un push. Después, rompe un test a propósito y mira cómo aparece la ❌ roja.
