En el [post sobre Swagger]({% post_url 2026-11-09-swagger %}) vimos que Swagger UI no se inventa nada: lee un **archivo** que describe la API y lo convierte en una página que puedes leer y probar. Hoy abrimos ese archivo.

Siguiendo con el restaurante: si Swagger es la carta bonita que te dan en la mesa, **OpenAPI es el contenido de la carta**: qué platos hay, qué lleva cada uno y cuánto cuesta.

## ¿Qué es OpenAPI?

OpenAPI es un **estándar para describir APIs** en un archivo. En ese archivo se apunta todo lo que alguien necesita saber para usar tu API:

- Qué endpoints tiene y qué método usa cada uno.
- Qué parámetros y datos hay que enviar.
- Qué devuelve cada endpoint y con qué códigos de estado.
- Si hace falta autenticación, y de qué tipo.

Lo bueno de que sea un estándar es que el archivo lo entienden **tanto las personas como los programas**. Una persona lo puede leer, y herramientas como Swagger UI lo pueden convertir en documentación, generar código a partir de él o usarlo para hacer pruebas.

El archivo se puede escribir en **YAML** o en **JSON**. Las dos formas son equivalentes, pero casi todo el mundo usa YAML porque se lee mejor, así que es el que usaré en este post.

Como vimos en el post de Swagger, el estándar se ha ido renovando. La versión 2.0 todavía se llamaba Swagger, y desde la 3.0 ya se llama OpenAPI. En los ejemplos usaré la **3.1**, que es la más extendida hoy en día.

## Un repaso rápido de YAML

Si no has usado YAML nunca, solo necesitas tres reglas para seguir este post:

```yaml
nombre: Astrid          # clave: valor
direccion:              # un valor puede contener otras claves...
  ciudad: Madrid        # ...indentadas debajo, con espacios
lenguajes:              # una lista: cada elemento empieza con guion
  - Python
  - JavaScript
```

1. Cada dato es `clave: valor`.
2. **La indentación importa**: lo que está más a la derecha pertenece a la clave de encima. Usa siempre espacios, nunca tabuladores.
3. Las listas se escriben con un guion `-` delante de cada elemento.

Con `#` puedes escribir comentarios, que se ignoran.

## Las partes de un archivo OpenAPI

Un archivo OpenAPI tiene unas pocas partes principales:

| Parte | Qué contiene |
|---|---|
| `openapi` | La versión del estándar que usa el archivo |
| `info` | Información sobre tu API: título, descripción y versión |
| `servers` | Dónde está la API (su URL) |
| `paths` | Los endpoints. Es la parte más importante |
| `components` | Piezas reutilizables: modelos de datos, seguridad… |

El archivo más pequeño posible sería algo así:

```yaml
openapi: 3.1.0
info:
  title: API de usuarios
  description: Una API de ejemplo para gestionar usuarios.
  version: 1.0.0
servers:
  - url: https://api.ejemplo.com
paths: {}
```

Ojo con no confundir las dos versiones: `openapi: 3.1.0` es la versión **del estándar**, y `version: 1.0.0` dentro de `info` es la versión **de tu API**, que subirás cuando la cambies.

`paths: {}` significa que todavía no hay ningún endpoint. Vamos a añadirlos.

## Describir un endpoint

Empecemos por el endpoint del [post de APIs]({% post_url 2026-11-09-que-es-una-api %}), `GET /usuarios/{id}`, que devuelve los datos de un usuario:

```yaml
paths:
  /usuarios/{id}:
    get:
      summary: Obtener un usuario por su id
      parameters:
        - name: id
          in: path
          required: true
          description: El id del usuario
          schema:
            type: integer
      responses:
        '200':
          description: El usuario existe
          content:
            application/json:
              schema:
                type: object
                properties:
                  id:
                    type: integer
                  nombre:
                    type: string
                  email:
                    type: string
        '404':
          description: No hay ningún usuario con ese id
```

Vamos por partes:

- **`/usuarios/{id}`** es la ruta del endpoint. Lo que va entre llaves es una parte variable.
- **`get`** es el método. Debajo de una misma ruta puedes poner varios: `get`, `put`, `patch`, `delete`…
- **`summary`** es una frase corta que explica qué hace. Es lo que verás al lado del endpoint en Swagger UI.
- **`parameters`** son los parámetros que acepta. Cada uno lleva:
  - `name`: su nombre.
  - `in`: dónde va. Puede ser `path` (dentro de la ruta, como aquí), `query` (después de la `?`, como en `/usuarios?pagina=2`) o `header` (en las cabeceras).
  - `required`: si es obligatorio. Los parámetros de tipo `path` siempre lo son.
  - `schema`: qué tipo de dato es (`integer`, `string`, `boolean`…).
- **`responses`** son las posibles respuestas, una por cada [código de estado]({% post_url 2026-11-09-que-es-una-api %}#los-códigos-de-estado). Cada una tiene una `description` y, si devuelve datos, un `content` que dice en qué formato (`application/json`) y con qué forma (`schema`).

Los códigos de estado van entre comillas (`'200'`) porque OpenAPI espera texto, y sin comillas YAML los leería como números.

## Enviar datos: requestBody

Para crear un usuario hacemos un `POST /usuarios` y enviamos sus datos en el cuerpo de la petición. Ese cuerpo se describe con `requestBody`:

```yaml
paths:
  /usuarios:
    post:
      summary: Crear un usuario
      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              required: [nombre, email]
              properties:
                nombre:
                  type: string
                email:
                  type: string
                edad:
                  type: integer
      responses:
        '201':
          description: Usuario creado
        '400':
          description: Faltan datos o son incorrectos
```

La forma es la misma que en las respuestas: un `content` con el formato y un `schema` con los campos. La novedad es `required: [nombre, email]`, la lista de campos obligatorios. La edad se puede enviar o no.

## No repetirse: components y $ref

Fíjate en que ya hemos escrito los campos de un usuario dos veces: en la respuesta del GET y en el cuerpo del POST. Si añadimos un `PATCH`, un `PUT` y un endpoint para listar usuarios, tendríamos que copiarlos tres veces más. Y si un día añadimos un campo, habría que cambiarlo en todos los sitios.

Para no repetirnos, definimos el usuario **una sola vez** dentro de `components`, en `schemas`:

```yaml
components:
  schemas:
    Usuario:
      type: object
      required: [nombre, email]
      properties:
        id:
          type: integer
          readOnly: true
          example: 1
        nombre:
          type: string
          example: Astrid
        email:
          type: string
          format: email
          example: astrid@ejemplo.com
        edad:
          type: integer
          minimum: 0
          example: 25
```

Y en cada sitio donde aparece un usuario, en lugar de copiar los campos, lo **referenciamos** con `$ref`:

```yaml
schema:
  $ref: '#/components/schemas/Usuario'
```

Esa ruta se lee como "en este mismo archivo (`#`), ve a `components`, luego a `schemas`, y coge `Usuario`".

De paso he añadido algunas cosas útiles al esquema:

- **`example`**: un valor de ejemplo. Swagger UI lo usa para rellenar los ejemplos de la documentación.
- **`format: email`**: da más detalle sobre el tipo. No es solo un texto, es un email.
- **`minimum: 0`**: una restricción. La edad no puede ser negativa.
- **`readOnly: true`**: el `id` solo aparece en las respuestas, nunca se envía. Tiene sentido: como vimos en el post de APIs, el id lo asigna el servidor al crear el usuario. Gracias a esto podemos usar el mismo esquema `Usuario` para enviar y para recibir.

## Endpoints protegidos: seguridad

Muchas APIs piden un token para saber quién hace cada petición, como los [JWT]({% post_url 2026-11-09-jwt %}). En OpenAPI esto se describe en dos pasos.

Primero, en `components`, defines **qué tipo de autenticación** usa la API y le pones un nombre (aquí, `bearerAuth`):

```yaml
components:
  securitySchemes:
    bearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT
```

Esto significa: "el token se envía en la cabecera `Authorization: Bearer <token>`, y es un JWT".

Después, con `security`, dices **dónde se aplica**. Si lo pones en la raíz del archivo, se aplica a todos los endpoints:

```yaml
security:
  - bearerAuth: []
```

Y si algún endpoint es público, como el de iniciar sesión o el de registrarse, lo indicas en ese endpoint con una lista vacía:

```yaml
paths:
  /login:
    post:
      security: []
```

Esto es justo lo que hace aparecer el botón **Authorize** en Swagger UI. Pegas ahí tu token y se envía en todas las peticiones protegidas.

## El archivo completo

Juntando todo, este es el archivo de nuestra API de usuarios:

```yaml
openapi: 3.1.0
info:
  title: API de usuarios
  description: Una API de ejemplo para gestionar usuarios.
  version: 1.0.0
servers:
  - url: https://api.ejemplo.com

security:
  - bearerAuth: []

paths:
  /usuarios:
    post:
      summary: Crear un usuario
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/Usuario'
      responses:
        '201':
          description: Usuario creado
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Usuario'
        '400':
          description: Faltan datos o son incorrectos
        '401':
          description: No has enviado un token válido

  /usuarios/{id}:
    get:
      summary: Obtener un usuario por su id
      parameters:
        - name: id
          in: path
          required: true
          description: El id del usuario
          schema:
            type: integer
      responses:
        '200':
          description: El usuario existe
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Usuario'
        '401':
          description: No has enviado un token válido
        '404':
          description: No hay ningún usuario con ese id

components:
  schemas:
    Usuario:
      type: object
      required: [nombre, email]
      properties:
        id:
          type: integer
          readOnly: true
          example: 1
        nombre:
          type: string
          example: Astrid
        email:
          type: string
          format: email
          example: astrid@ejemplo.com
        edad:
          type: integer
          minimum: 0
          example: 25

  securitySchemes:
    bearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT
```

Como los dos endpoints están protegidos, los dos pueden responder con un **401**, y lo he añadido a sus respuestas.

## Pruébalo tú: Swagger Editor

Abre [editor.swagger.io](https://editor.swagger.io), borra el ejemplo que trae y pega el archivo completo. A la derecha verás la misma página de Swagger UI que vimos en el post anterior, pero con **tu** API: los dos endpoints, el esquema `Usuario` con sus ejemplos y el botón **Authorize**.

Algunos retos para practicar:

- Añade el campo `telefono` al esquema `Usuario` y fíjate en que aparece en los dos endpoints a la vez. Esa es la gracia de `$ref`.
- Añade un `DELETE /usuarios/{id}` que responda con un **204**.
- Quita un espacio de la indentación en cualquier línea. El editor te marcará el error, y así ves por qué la indentación importa tanto en YAML.

> Los botones **Try it out** no te van a funcionar aquí, porque `api.ejemplo.com` no existe. Para probar peticiones de verdad necesitas una API que esté funcionando, como la demo Petstore del post anterior.

## ¿Escribir el archivo a mano o generarlo?

Hay dos formas de trabajar con OpenAPI:

- **Code-first (primero el código):** programas la API y el framework genera el archivo OpenAPI a partir del código. Es lo que vimos en el post de Swagger con FastAPI. Es lo más rápido y la documentación siempre está al día.
- **Design-first (primero el diseño):** escribes el archivo OpenAPI antes de programar nada, y después programas la API siguiéndolo. Es útil cuando trabajan varios equipos: por ejemplo, frontend y backend se ponen de acuerdo en el archivo y cada uno empieza a trabajar por su lado sin esperar al otro.

Ninguna es mejor que la otra; depende del proyecto y del equipo. Pero aunque el archivo lo genere tu framework, saber leerlo te va a servir: para entender qué ha generado, para corregirlo cuando algo no salga bien y para leer la documentación de otras APIs.

## Más allá de Swagger: qué más se puede hacer con el archivo

Como OpenAPI es un estándar, no solo lo entiende Swagger. Con el mismo archivo puedes:

- **Generar otra documentación:** por ejemplo, [Redoc](https://github.com/Redocly/redoc) crea una página de documentación con otro diseño.
- **Generar código:** [OpenAPI Generator](https://openapi-generator.tech) crea clientes para usar la API desde muchos lenguajes, sin escribirlos a mano.
- **Probar la API en Postman:** puedes importar el archivo y Postman te crea todas las peticiones.
- **Crear un servidor falso (mock):** un servidor que responde con los ejemplos del archivo, para que el frontend pueda trabajar aunque el backend aún no esté listo.
- **Validar:** comprobar automáticamente que las peticiones y respuestas reales cumplen lo que dice el archivo.

Por eso a menudo se dice que el archivo OpenAPI es el **contrato** de la API: deja por escrito lo que la API promete hacer, y cualquiera (persona o programa) puede comprobarlo.

## Para terminar

OpenAPI es un estándar para describir una API en un archivo YAML o JSON: sus endpoints, los datos que reciben y devuelven, sus códigos de estado y su seguridad. Con `components` y `$ref` defines cada cosa una sola vez, y con ese único archivo herramientas como Swagger generan la documentación, el código o las pruebas.

Si quieres seguir practicando, coge una API que conozcas y prueba a describir un par de sus endpoints en Swagger Editor.
